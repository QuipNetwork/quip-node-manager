# v0.2 Runtime Migration Plan

This plan records the changes needed for `quip-node-manager` based on the
checked-out `../nodes.quip.network` `v0.2` branch compared with its `main`
branch.

## Summary

`nodes.quip.network` v0.2 is a runtime migration, not a Docker image tag bump.
The deployment model changes from one monolithic `quip-node` container to a
substrate-aware miner plus a local validator and bootstrap step.

Important upstream changes:

- Miner images changed from `quip-network-node-{cpu,cuda}:latest` to
  `quip-miner-{cpu,cuda}:v0.2-preview`.
- A validator image is now part of the standard stack:
  `quip-protocol-rs/quip-network-node:v0.2-preview`.
- Fresh miners need a bootstrap registration step before normal startup.
- The miner config schema is now documented and tested as `[miner]`, with
  `validators` and `signer_key` replacing legacy P2P settings.
- Caddy is needed for the public v0.2 surface and should be part of the manager
  runtime.
- Dashboard and Postgres are part of the `nodes.quip.network` operator stack,
  but are not needed for the first v0.2 manager milestone.

## Config Changes

Current manager config generation is still v0.1-shaped:

- `[global]`
- `listen`
- `port`
- `secret`
- `genesis_config`
- `peer`
- `timeout`
- `heartbeat_*`
- TLS and TOFU keys

For v0.2 miners, generate `[miner]` instead:

```toml
[miner]
validators = ["ws://quip-validator:9944"]
signer_key = "/data/keystore.json"
rest_host = "0.0.0.0"
rest_port = 80
```

The schema is shared by Docker and native miners. `RunMode` should only affect
runtime-specific values:

- Container miners use `validators = ["ws://quip-validator:9944"]` and
  `signer_key = "/data/keystore.json"`.
- Native Metal miners use a host-reachable validator URL, initially
  `validators = ["ws://127.0.0.1:9944"]`.
- Native Metal miners use a host filesystem signer path, initially
  `<data-dir>/keystore.json`.
- Native Metal miners use host filesystem log paths, initially
  `<data-dir>/logs/quip-node.log`.
- Native Metal telemetry should use a non-privileged host port that Caddy can
  proxy to, initially `rest_port = 20080`.

Preserve backend sections where applicable:

- `[cpu]`
- `[gpu]`
- `[cuda.N]`
- `[metal]`
- `[modal]`
- `[qpu]`
- `[dwave]`

Use `../nodes.quip.network/scripts/upgrade-config.py` as the migration rule
reference. Existing `[global]` configs should be backed up and rewritten rather
than edited in place.

## Runtime Control Decision

Use individual container orchestration in the manager instead of adopting
`docker compose` wholesale.

Reasoning:

- The manager already owns start, stop, status, logs, update checks, and UI
  state. Running a single Compose stack would hide too much service-level state.
- The Metal miner runs without Docker. A Compose-first model assumes the miner
  is a container, which is the wrong abstraction on macOS Metal.
- Fine-grained service control lets the manager run support services in Docker
  while running the miner either as a container or as a native process.
- Individual containers make it easier to recover from partial failures:
  validator running, bootstrap failed, miner stopped, dashboard unavailable,
  etc.
- Compose remains useful as the upstream behavioral spec. The manager should
  mirror the required images, env vars, volumes, network aliases, ports, and
  startup ordering, not necessarily the Compose implementation.

## Proposed Service Model

Create a manager-owned Docker network, for example `quip-node-manager`.

Core services:

- `quip-validator`: substrate validator container.
- `quip-bootstrap`: one-shot bootstrap container that registers and funds the
  miner account.
- `quip-cpu` or `quip-cuda`: containerized miner when using CPU or CUDA Docker
  mode.
- Native miner process: used for Metal and other native modes.

Optional services:

- `quip-dashboard`: bundled dashboard, postponed until there is a concrete UI
  need.
- `quip-postgres`: dashboard persistence, only needed if dashboard is enabled.

Initial v0.2 compatibility should prioritize the core services required for
the node to start correctly. Caddy should be included because it fronts the
public API/RPC surface. Dashboard and Postgres should remain optional.

## Native Metal Analysis

Metal is not available inside Docker because Docker Desktop runs Linux
containers in a VM. The v0.2 manager design must support this shape:

```text
Docker:
  quip-validator
  quip-bootstrap
  quip-caddy
  optional dashboard/postgres

Native:
  quip-miner with [metal]
```

Implications:

- The native Metal miner should connect to a validator endpoint reachable from
  the host, not a Docker-only alias. Candidate value:
  `validators = ["ws://127.0.0.1:9944"]`.
- The native Metal miner should still use the same v0.2 `[miner]` schema as
  Docker miners. Only endpoint and filesystem path values should differ.
- The validator container may need to publish RPC to localhost for native
  miners, for example `127.0.0.1:9944:9944`.
- If Caddy runs in Docker and must proxy to a native miner REST endpoint, the
  container needs a stable host route. On macOS and Windows this is usually
  `host.docker.internal`; on Linux this likely requires
  `--add-host=host.docker.internal:host-gateway`.
- Caddy must be able to expose native Metal miner telemetry through
  `/api/v1/*`. For native miners, the upstream should point at the host-side
  miner REST endpoint instead of the Docker alias used by container miners.
- The manager should not assume the miner and validator always share Docker DNS.
  Validator URLs should be generated based on the selected miner runtime:
  container miner uses `ws://quip-validator:9944`; native miner uses a host
  reachable URL.
- Bootstrap still needs access to the same signer key that the native miner
  will use. If the signer key is host-owned, mount it into the bootstrap
  container at `/data/keystore.json` or run bootstrap natively if available.

Open validation item: confirm the exact native v0.2 miner bootstrap and
keystore workflow for Metal before final implementation.

## Bootstrap Flow

Fresh v0.2 miners fail until their signer account is registered in
`QuantumPow.Miners`. The manager should model bootstrap as a first-class step:

1. Ensure data directory and config exist.
2. Ensure signer key exists or let the entrypoint create it.
3. Start validator.
4. Run `quip-bootstrap` equivalent:
   `quip-miner bootstrap --validator ws://quip-validator:9944 --signer-key /data/keystore.json --faucet-url ...`
5. Start miner only after bootstrap succeeds.

The bootstrap step should be idempotent and visible in the UI/logs.

## Checklist Decision

Postpone adding a `30333` public port check until after the v0.2 runtime
migration lands.

Reasoning:

- Current checklist is still based on the v0.1 single-node port model.
- `30333/tcp+udp` belongs to the validator, not the miner.
- The manager first needs a reliable v0.2 service model before checklist
  results can map cleanly to services.
- After v0.2 lands, add separate checks for:
  `20049/tcp` for Caddy/public API and `30333/tcp+udp` for validator libp2p.

The v0.2 implementation may still map `30333` for validator containers. This
decision only defers checklist validation and user-facing diagnostics for that
port.

Also postpone `80/tcp` and `443/tcp` checks unless and until the manager supports
production hostname/TLS mode.

Reasoning:

- `80` and `443` are only needed when `QUIP_HOSTNAME` is a real hostname and
  Caddy should issue a public certificate.
- Local/dev mode can use `QUIP_HOSTNAME=:20049`, where Caddy serves HTTP on
  `20049` and does not need ACME.
- If production TLS mode is added, the manager should then validate that Caddy
  can bind `80` and `443` and that those ports are exposed to the internet.

## Implementation Phases

### Phase 1 - Generate Valid v0.2 Config

- Add v0.2 config rendering for all miner run modes.
- Keep one shared `[miner]` schema and vary only runtime-specific values such
  as validator URL, signer-key path, and telemetry port.
- Add tests that generated v0.2 TOML contains `[miner]`, `validators`, and
  `signer_key`.
- Add tests that generated v0.2 TOML does not contain legacy `peer`, `secret`,
  `trust_db`, or P2P listener keys.

### Phase 2 - Individual Container Runtime

- Add image constants and tag settings for miner and validator images.
- Create or reuse a manager-owned Docker network.
- Start, stop, inspect, and stream logs per service.
- Start validator first, then bootstrap, then miner.
- Track status per service rather than only `quip-node`.

### Phase 3 - Native Metal Runtime

- Define host-reachable validator URLs for native miners.
- Decide whether bootstrap uses a container with a mounted signer key or a
  native binary.
- Verify native Metal miner startup against the v0.2 validator.
- Keep Docker-only assumptions out of shared config and UI state.

### Phase 4 - Caddy Public Surface

- Run Caddy by default for the v0.2 public surface.
- Add Caddy routing for both container miners and native miners.
- For container miners, proxy `/api/v1/*` to `quip-miner:80`.
- For native Metal miners, proxy `/api/v1/*` to the host-side miner REST
  endpoint through a stable Docker-to-host route.
- Keep dashboard and Postgres postponed and optional.

### Phase 5 - v0.2 Checklist And Diagnostics

- Replace legacy node-secret checks with signer-keystore checks.
- Replace bootstrap peer wording with validator wording.
- Add `20049/tcp` public API check.
- Add `30333/tcp+udp` validator libp2p check after the runtime migration.
- Add `80/tcp` and `443/tcp` checks only if production hostname/TLS mode is
  implemented.

## Immediate Next Steps

1. Verify the actual `quip-miner` image accepts `[miner]` as canonical config.
2. Implement the first v0.2 manager milestone with miner, validator, bootstrap,
   and Caddy; keep dashboard/Postgres optional and postponed.
3. Implement config rendering tests before changing runtime orchestration.
4. Implement individual container lifecycle helpers and test with CPU mode.
5. Validate the native Metal path separately before changing macOS defaults.
